今天学了 git：一个新手理解的源代码管理

发表于2026-10-09|更新于2026-10-09|折腾记录

写在最前面：这篇是借助 DSH 写出来的。我提供思路和经历，它帮我把话说清楚、把命令写准。
这一点我不想含糊——毕竟下面这些内容里，有一部分确实是它替我梳理的。

先说一个感慨

今天最大的感受是：用 AI 学东西，真的方便得有点不真实。

以前遇到”git 是什么、怎么回滚”这类问题，我要么在搜索引擎里翻十几篇文章，
要么在论坛里问、等回复、再自己试错。现在可以直接问，而且能拿到针对我这个具体项目的答案——
不是泛泛的教程，是”你这台机器上这条命令会走哪条通道、失败了怎么办”。

但今天也让我看清了另一件事：方便不等于省事。

工具帮你把动作做完了，判断和验证还是得自己来。今天有两个例子让我印象特别深，下面会写。

学 git 之前，我连这个词都说不清

在跟 DSH 聊之前，我自己先看了一些 git 的基础。

我原来对 git 的理解大概是：“一个能保存代码历史的东西”。
再具体一点就说不出来了——什么是提交、什么是分支、什么叫远端，都是模糊的。

自己看了一遍之后，我至少搞明白了**”源代码管理”（Source Control）这个概念本身是干什么的**：

它管理的不是”代码”，而是代码的变化过程。
你每做一次改动就存一个档，标上说明。以后想看看”三天前那个能跑的版本长什么样”，
或者”这次改坏了，退回去”，都能做。

理解了这一点，再看命令就不觉得是在背咒语了：

命令 它在干什么
git status 现在有哪些文件改了、还没存档
git add 把改动放进这次要存的范围
git commit 存一个档，配一句说明
git log 看所有存档点
git push 把存档同步到远端（GitHub）

存了档才能回退——这是我今天最重要的一个观念转变。
以前我以为”回退”是某种魔法，其实它只是”回到某个存档点”。

真正让我搞明白的，是把它套到自己的项目上

概念懂了，但一放到我这个博客上就乱了：我这里有两个仓库。

DSH 帮我理清之后我才明白，git 在我这个站点里扮演的是两种完全不同的角色：

仓库 git 在这里做什么
st4awber-hexo-source（源码） 真正的版本管理 —— 每个提交是存档点，能对比、能回退
st4awber.github.io（网页） 只是个投递通道 —— 被自动构建整棵覆盖，历史没有意义

这里有个特别反直觉的点，我记下来了：

回滚网站，根本不需要动那个网页仓库。
因为线上是从源码重新生成的——我把源码退回旧状态再推一次，
重新生成出来的就是旧网站。

我以前一直以为”网站的文件”才是正主，其实它只是生成物。
真正的”原稿”是源码仓库，而版本管理的价值全在那边。

我踩过的一个认知坑：把”备份”当成源代码管理

写第一篇文章的时候我提过：四月我重装系统，本地源码没备份，项目就搁置了。

今天我才意识到，那不只是”没备份”的问题。

就算我当时备份了文件夹，如果没有提交历史，那我照样不知道：

  • 哪次改动把东西弄坏了
  • 三天前那个能跑的版本是什么样
  • 这个文件为什么变成现在这样

备份保存的是”最后一刻”，源代码管理保存的是”整个过程”。 这是两件事。

一个意外的发现：本地和远端可以是两条历史线

查我这个仓库的时候发现一件怪事：

提交数 内容
远端（GitHub） 11 个 4 月的 3 个原创 + 后来推的 8 个
本地（我的电脑） 17 个 恢复源码之后的所有提交

两边文件内容一模一样，但提交历史是两条独立的线。

为什么会这样，我大致明白了：

  • 四月那次，本地文件丢了，但远端的提交历史还在（里面还有我最初的三个提交：
    初始化 Hexo 博客源码、更新部分美化+功能、美化）
  • 后来恢复源码时，这台机器上还没装 git，只能新建一个仓库——内容补回来了，历史没继承
  • 再后来推送时，git push 在这个网络下连不上 GitHub，只能走 GitHub 的 API 推送。
    API 推送的方式是”以远端当前提交为父提交，把当前文件打成一个新快照”，
    所以远端的历史一直保留着，而我本地是另一条更细的线

这件事让我理解了 git 一个很重要的性质：历史是”链条”，内容一样不代表历史一样。

只要内容对得上，两条线并存也不影响使用。但这也带来一个真实的风险，见下面。

回滚：我搞清楚了三种情况

这是我最想学会的东西——“改坏了怎么办”。

情况一：改动还没存档，想丢掉

情况二：已经存档了，想撤销这次存档

revert 的特点是不删历史——它只是加一个新提交把改动抵消。这对新手最友好。

情况三：让线上网站回到旧版本（真正的回滚）

第 4 步有个细节我记下来了：reset --hard 之后工作区是干净的，
所以日常那个发布脚本会认为”没东西可发”而退出——回滚要用另一个脚本
（import-via-git-api.ps1），它是”不管有没有变化，直接把当前完整状态推上去”。

唯一绝对不能做的事

不要 git push --force（强推）。

这是我今天听到的最重的警告。原因就在上面那个”两条历史线”：
本地和远端是两条无关的线，强推会用本地历史覆盖掉远端，
那我四月那三个原创提交就永远没了。

DSH 特意把远端那三个提交的哈希列出来给我看，说”这些请保住”。
我觉得这个做法很对——不是笼统地说”小心点”，而是把具体会失去什么摆出来。

救命命令：git reflog

这个命令会记录你做过的所有操作，包括被 reset 掉的、看起来已经”走远”的提交。

理解了这一点，我对 git 的恐惧感少了一大半：

改坏了不可怕。 只要你别强推，绝大多数错误都能找回来。

两个让我改变看法的瞬间

今天有两件事，让我对”用 AI 学东西”这件事的看法具体了很多。

第一件：AI 也会犯错，而且错得很隐蔽

改鼠标拖尾效果的时候，脚本突然整个失效了——拖尾没了、鼠标点击的粒子也没了。

查出来的原因很典型：它自己做全局替换时误伤了变量定义，
把一个取时间的辅助函数写成了”调用自己”，于是脚本一执行就无限递归、直接崩溃。

值得说的是它怎么发现并修好的：

  1. 它没有靠”看起来对”——而是写了个最小的 DOM 桩，在 Node 里把那个脚本真的跑了一遍，
    确认”初始化成功，没有抛错”
  2. 修完之后还专门核对：return now() 这种自调用已经不存在

这件事告诉我：AI 的执行力很强，但它也需要”验证”这一步。
而验证这件事，有时候需要一个外部的人说”不对，还是没效果”。

第二件：我的一个观察，帮它纠正了方向

还有一个 bug 更离奇：浅色模式下整个页面发黑，深色模式却完全正常。

它查了一圈 CSS，说”代码里没有任何规则会让浅色变黑”。

我随口提了一句我的操作方式：我是用网页右下角的齿轮切换深浅色的——
结果这句话让它想到了方向：问题不在网站代码，而在浏览器装的深色模式扩展。
那个扩展在强行给”浅色页面”反色，body 背景被它改成了 #181a1b——
一个我的 CSS 里根本不存在的颜色。

这就是我想说的：AI 能查得比我快一万倍，但它不知道我的操作细节。
“我是怎么点的”这种信息，只有我知道。 我给了一条线索，它就省下了一大圈弯路。

所以关于用 AI，我的结论是

方便是真的方便，但它改变的是我该做什么，不是让我什么都不用做。

以前 现在
查资料 翻十几篇文章 直接问，还能问得很具体
试错 自己反复撞墙 它帮我撞，把坑列出来
我的工作 敲命令、记语法 提供信息 + 判断结果

今天最值钱的几件事都是这么发生的：

  • 我告诉它”我是用齿轮切换的” → 它找到了真正的 bug
  • 我告诉它”拖尾还是没出来” → 它才去查那个无限递归
  • 我把 Vercel 的截图发过去 → 它才定位到评论那三个叠加的坑

我不是在”用”它，更像是在”带”它 —— 我提供现场，它负责跑腿和整理。

对我这种新手来说，这个分工其实挺好的：
我不用先花三个月学会所有语法，才能开始做一件想做的事。

接下来

我打算把 git 用得更自然一些——不只是在发布的时候用，而是养成”改一段就存一个档”的习惯。

毕竟今天才真正明白：存档不是为了发布，是为了让自己敢改。

改坏了能退回去，才敢大胆地试。

这篇的 git 操作细节，我整理进了站点的新手操作手册（第 13 节），包括那两个仓库的分工、回滚的三种情况，以及为什么不能强推。
