从零把这个博客修好：一次真正走完的搭建过程

发表于2026-09-18|更新于2026-09-18|折腾记录

一个搁置了五个月的想法

今年四月，我因为一阵突然的热情，想给自己弄一个独立的博客。

那时候学了一点东西：Hexo 能把我写的 Markdown 变成静态网页，Butterfly 主题能让它看起来像样，
GitHub Pages 能免费托管，hexo deploy 能一键发布。照着教程走一遍，站点确实跑起来了——
首页有背景图，头像能转，还有鼠标拖尾。

然后就没有然后了。

后来重装系统，本地那份源码没备份。等我再想起来的时候，本地是空的，
线上只剩两个仓库：一个装着编译好的网页，一个装着源码——而源码那个，我连它叫什么作用都忘了。

这件事就这么搁着，一直到今天。

今天为什么又捡起来了

最近在写简历，需要放一个作品链接。翻出这个半成品，看着那个只有一篇 “Hello World” 的站点，
突然觉得有点不甘心——它不是做不成，是我没做完。

于是今天借助 DSH，把它从”能看”推到了”能用”。

为什么源码还在，却打不开了

这是今天第一个、也是最要命的问题。

我手上其实有源码仓库，git clone 下来一看，主题文件夹是空的。

查了半天才明白：这个仓库里 themes/butterfly 是一个 git submodule（子模块）。
子模块在 GitHub 上只是一个”指针”，记录”要去哪个仓库、取哪个版本”，
它的内容不在父仓库里。所以下载压缩包也好、浅克隆也好，那个目录都是空的。

教训一：子模块是个隐形陷阱。它让仓库看起来完整，实际缺一大块。
如果只是自己用，把它当普通目录提交进去更省心。

后来按它指向的那个精确版本把主题补回来，问题才解决。

源码比线上还旧

补完主题，第二个问题来了：源码仓库里少了一堆文件。

比如背景图 bg.avif、头像、favicon.png，还有一个鼠标特效脚本 mouse-lines.js——
这些东西线上站点里有，源码仓库里没有。

说明当时改完是直接部署到线上的，但忘了提交到源码仓库。

教训二：部署 ≠ 提交。这两个动作是分开的。
建议养成习惯：改完先提交，再部署；或者干脆让 CI 自动做这件事（见下文）。

我是从线上站点里把这些文件”反向”取回来的——因为它们就静静地躺在编译产物里。

一个很小、但会让所有旧链接失效的坑

有一篇文章叫 hello-world.md，它的开头是这样的：

没有 date 字段。

Hexo 遇到这种情况会拿文件的修改时间当发布日期。而修改时间取决于你什么时候把文件复制到硬盘上——
所以我本地构建出来，这篇文章的网址变成了 /2026/09/18/hello-world/，而线上是 /2026/04/14/。

任何一次重新构建，都会让这篇文章的链接失效。

教训三：文章的 date 一定要显式写。
网址稳定是博客的基本要求，别让文件的修改时间决定你的 URL。

YAML 里少一个空格，整站构建失败

配置评论系统的时候，我写了这么一行：

然后构建直接崩了：

YAML 里 键:值 和 键: 值 是完全不同的东西。 少了那个空格，
整行会被解析成一个奇怪的键名，进而让整个文件解析失败——
不是评论不显示，是整个站点都构建不出来。

教训四：改 .yml 文件时，冒号后面永远记得敲一个空格。
而且一旦报错，先看报错的行号，它指得很准。

自动部署：让网站自己更新

今天最值得的一件事，是把它接到了 GitHub Actions 上。

逻辑很简单：我把改动推到源码仓库，GitHub 的服务器自动帮我构建，再把结果发布到站点仓库。

我的电脑关机也照样更新。 不用再记住”构建、复制、部署”这一串动作。

过程中遇到的坑：

  • 工作流需要一个令牌才能把结果推到另一个仓库，这个令牌要放在仓库的 Secret 里，
    不能写进代码——因为仓库是公开的，写进去等于把钥匙贴在门上
  • 还有一个特别隐蔽的问题：子模块的”指针”和普通文件冲突，
    用 API 构建文件树时会报 422 BadObjectState，最后改成从零重建整棵树才绕过

评论系统：三个问题叠在一起

我想给站点加评论。选了 Waline，理由是数据存在自己的数据库里，不依赖第三方平台。

结果一连踩了三个坑，而且是叠加的——只修一个都不管用：

# 问题 现象
1 YAML 少一个空格 整个站点构建失败
2 Vercel 里项目重名，地址填错了 打开评论地址看到的是博客首页
3 数据库连接后没有重新部署 服务端 500，函数一启动就崩

第 3 个特别反直觉：环境变量只在”部署的那一刻”注入。
数据库是后来才连上的，所以当时正在运行的那份代码根本看不到它，一启动就崩。
连完数据库必须手动 Redeploy 一次。

教训五：遇到 500 先去服务端看日志，那里写着真正的原因。
我在外面猜了很久，最后是靠一行 No valid storage found 才定位的。

一个查不到的 bug

改完外观，出现了最诡异的现象：

  • 深色模式：完全正常
  • 浅色模式：整个页面发黑，文字糊成一团

我翻了构建出来的所有 CSS，浅色模式下没有任何一条规则会把页面变黑。

最后在浏览器控制台里查到一个数字：

而我写的浅色模式背景是 #fff（纯白）。

#181a1b 这个颜色不是我的 CSS 里的——它是浏览器深色模式扩展（Dark Reader 之类）
强行给”浅色页面”加的兜底底色。

关掉扩展，一切正常。

教训六：代码里查不到的问题，要去运行时找证据。
我拿着”确凿的代码”判断了很久，其实方向从一开始就错了。
另外，装深色模式扩展的话，最好把自己常访问的站点加进例外。

最后，一件必须说的事

我今天最大的体会不是任何一个技术点，而是：“没做完”和”做不成”是两件事。

这个博客今天是”做完了”——它能构建、能预览、能自动发布、能评论、外观也调到了自己喜欢的样子。
剩下唯一缺的东西是内容，而那是需要我自己一句一句写出来的。

接下来会写什么

我打算在这里记录三类东西：

  • 技术上踩过的坑 —— 像今天这种，写下来对自己是备忘，对别人可能正好有用
  • 一些学习和折腾的过程 —— 我是怎么一点点弄明白一件事情的
  • 生活里值得留下的片段 —— 不一定和代码有关

更新频率我不敢承诺，但我希望它一直在。

毕竟这个站点已经能自己更新了，剩下的只是我别再一次次地”搁置”它。

如果你也在折腾 Hexo 或者静态博客，今天这些坑我都记在站点的新手操作手册里了，希望能帮你少走一点弯路。
